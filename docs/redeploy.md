# 重新部署 MedHOT

线上实例跑的是一个**代码快照**。GitHub 上推了新代码，线上不会自动跟着变 —— 需要在手机
WorkBuddy 里让它重新部署。

- 线上地址：`https://a77a1a00298fa9921.app.workbuddy.host`
- 仓库：`github.com/taozi69/medhot`（私有）
- 部署方：手机 WorkBuddy（腾讯 CloudBase），本机无法触发

---

## 一、场景速查

| 你要做什么 | 发什么提示词 |
|---|---|
| 日常更新（改了代码、后台功能、阈值……） | **A** |
| 新增 / 修改了信源 | **B** |
| 回到某个确定的旧版本 | **C** |

**关键：日常一律拉 `main`，不要在提示词里写版本号。** 写死 tag 会让你下次加了新东西
还部署出旧版本。tag 只在场景 C 回滚时才用。

## 场景 A · 日常更新

改了代码，没动信源：

```
请拉取 taozi69/medhot 的 main 分支重新部署。

注意：
1. 部署前把沙箱里的 .env 完整备份出来，重建后恢复进去。
   .env 不在 Git 仓库里，代码重建不会带上它。
2. 数据库不要动、不要重建。
```

**部署后确认：** 后台能登录 → 新改的功能能看到。

## 场景 B · 新增 / 修改了信源

这一个场景最容易出错，因为**改了 `industry/sources.json` 不等于线上数据库就有了新信源**。

信源是在部署时由 `scripts/seed.ts` 灌进数据库的。seed 是**幂等**的（`ON CONFLICT (id) DO
NOTHING`）：只补数据库里没有的源，不动已有的 —— 所以后台手动改过的信源不会被覆盖，重新
跑也安全。但如果你不主动让它跑一次，新增的源就进不去。

```
请拉取 taozi69/medhot 的 main 分支重新部署。

注意：
1. 部署前把沙箱里的 .env 完整备份出来，重建后恢复进去。
2. 数据库不要动、不要重建。
3. 部署完成后请重新执行一次信源种子导入，让新增的信源进数据库：
   node --env-file=.env scripts/seed.ts
   这个脚本是幂等的，重复执行安全，不会覆盖后台已改过的信源。
```

**部署后确认（必做）：** 打开后台信源页，看总数是不是新的。
比如原来 80 个、这次新增 5 个，要看到 85。数字对上才算真的成功。

> seed 的输出会打印 `sources: N added, M already there`。N 是这次新增的数量，
> 和你在 `sources.json` 里加的数量对得上就说明没问题。

**新信源除了加进 `sources.json`，还要在本地先校验过：**

```bash
node scripts/m3-validate-all.mjs     # 应输出 sources=N  bad=0
```

`bad` 不为 0 说明某个源的 `config` 字段不被支持，推上去会导致 seed 中途报错。

## 场景 C · 回滚到某个确定版本

只有当新版本出问题、想退回旧版时才用。

```
请拉取 taozi69/medhot，切换到 tag medhot-v3.0.0 重新部署。

注意：
1. 部署前把沙箱里的 .env 完整备份出来，重建后恢复进去。
2. 数据库不要动、不要重建。
```

可用版本（`git tag -n1` 查看，或见仓库 Tags 页）：

| tag | 内容 |
|---|---|
| `medhot-v3.0.0` | 80 信源，CI 全绿 —— 当前稳定版 |
| `medhot-v2.2.2` | 测试对齐医疗 taxonomy |
| `medhot-v2.2.0` | 槽位泄漏修复 + 拉模型 / 测速 |
| `medhot-v2.0.0` | M2：74 信源 + 动态 LLM API Pool |
| `medhot-v1.0.0` | M1 首个医疗信源包 |

> ⚠️ 回滚**代码**不会回滚**数据**。如果新版本已经往数据库里加过信源或改过内容，退回旧
> 代码后这些数据还在。数据库结构如果变过（新增列、改约束），旧代码可能读不了新库 ——
> 这种情况要先确认迁移是否兼容。

## 三、`.env` 是什么，为什么每次都提

`.env` 是一个纯文本配置，存数据库地址、模型 Key、后台密码等。它**第一行就被 `.gitignore`
排除**，不在仓库里。仓库里只有 `.env.example`（模板，没有真实值）。

云端部署通常会清空工作目录重新拉代码。如果它不管 `.env`，重建后这个文件就没了：

| 丢了这个变量 | 症状 |
|---|---|
| `DATABASE_URL` | 服务启动即崩，日志报连不上数据库 |
| `ADMIN_PASSWORD` | 后台登不进去 |
| `SESSION_SECRET` | 登录后立刻被弹回登录页 |
| `LLM_API_KEY` | 能登录、无报错，但永远不出新文章 |
| `IMG_PROXY_SIGN_SECRET` | 文章配图全部裂开 |

完整的逐项核对清单见 `docs/deploy-env-checklist.md`。

**现在就去备份一份 `.env`。** 它只存在于那台部署机上，本机没有副本 —— 云端那份如果丢了，
你没有第二份可恢复。复制出来存到密码管理器，注意别发到聊天窗口。

## 四、本地推代码的标准动作

在 `E:/medhot/AIHOT`：

```bash
# 1. 改完东西先校验
npm run typecheck
node scripts/m3-validate-all.mjs          # 仅动了信源时

# 2. 提交
git add <改动的文件>
git commit -m "..."

# 3. 推送
git push medhot main

# 4. 等 CI 变绿（约 3~5 分钟）
#    https://github.com/taozi69/medhot/actions
#    确认绿了再让 WorkBuddy 部署，别把红的版本推上线

# 5. 打 tag（可选，但建议）
git tag -a medhot-v3.1.0 -m "新增 5 个信源，共 85"
git push medhot --tags
```

**版本号规则**（详见 `CHANGELOG.md`）：

- **主版本**：信源包换代（M1 → M2 → M3），数据或模式可能不兼容
- **次版本**：新增能力，向后兼容 —— 加信源属于这一档
- **补丁**：修 bug，不改数据与行为

一句话：**主版本看信源规模，次版本看后台功能，补丁看修 bug。**

## 五、故障对照

| 症状 | 最可能的原因 |
|---|---|
| 服务启动就崩、报连不上数据库 | `DATABASE_URL` 丢了 |
| 能打开页面但登不进后台 | `ADMIN_PASSWORD` 丢了 |
| 登录后立刻被弹回登录页 | `SESSION_SECRET` 丢了或变了 |
| 能登录、无报错，但一直没有新文章 | `LLM_API_KEY` 丢了或失效 |
| 代码改了但线上没有新功能 | 部署没真正更新 —— 检查是否拉到了最新 |
| 信源页数字没变 | 场景 B 漏了重跑 seed |
| 图片全部裂开 | `IMG_PROXY_SIGN_SECRET` 丢了 |
| 海外信源一直不更新 | `EGRESS_PROXY_URL` 丢了 |
